# Scalability assessment

User counts below are planning scenarios, not capacity predictions. The relevant load is concurrent requests, writes, session checks, email volume and admin query size. Production traffic, Postgres sizing and host topology are **Unknown / needs verification** (`README.md`, `docker-compose.yml`).

## Matters now

- **Public abuse control is durable but client IP remains unresolved.** Contact and email-list POSTs use atomic Postgres counters with separate per-destination and per-flow budgets (`src/server/rate-limit.ts`). Counters survive restarts, are shared among replicas, and expired keys are pruned in bounded batches; forged forwarding headers are ignored by these custom routes. Once a host is selected, add its verified client identity at the edge or application boundary so a global ceiling is not the only protection against rotating destination emails. Redis is not automatically required.
- **Admin data reads can grow without bound.** `listContactSubmissions` and `listEmailSubscribers` return every matching row, including full contact messages or subscriber metadata, and corresponding pages render all results (`src/server/db/dal/contact-submission.ts`, `src/server/db/dal/email-list.ts`, `src/app/admin/contact-submission/all/page.tsx`, `src/app/admin/email-list/submissions/page.tsx`). Add server pagination and bounded result sizes before these datasets grow.
- **Email work sits on request paths.** Verification/password/account messages await Resend; welcome email is detached with `void ...catch` from a Better Auth hook (`src/server/routes/email-list.ts`, `src/server/account/email-change.ts`, `src/lib/auth/index.ts`). The first raises request latency and provider-failure coupling; the latter can be lost if a serverless invocation ends. Prefer awaiting essential email and a durable outbox/retry only once delivery guarantees or volume justify it.
- **No observable production deployment/ops contract.** The repo provides `next build/start`, local Postgres and a constant health response (`package.json`, `docker-compose.yml`, `src/server/routes/index.ts`). Confirm runtime, DB migration procedure, backups, logs and email/upload configuration before relying on horizontal scaling.

## Around 10k users

- **Database connections:** `src/server/db/index.ts` caps each Node process at 10 production connections. Total possible connections equal replicas/invocations times that cap; compare against the managed database limit and add an external pooler or lower per-instance cap if needed. `prepare:false` is compatible with common poolers but does not itself provide one.
- **Admin users search:** `listAdminUsers` uses `ILIKE` patterns, flexible sort columns, `OFFSET` and a separate exact `COUNT(*)` (`src/server/db/dal/admin-users.ts`). The `user` schema indexes email uniqueness but not arbitrary name search/sorts (`src/server/db/schema/auth-schema.ts`). Measure `EXPLAIN ANALYZE` for actual admin filters before adding narrow indexes, trigram search or keyset pagination.
- **Default list seeding is explicit.** Built-in waitlist/newsletter rows are created by `pnpm db:seed`; public signup and admin reads no longer upsert defaults (`src/server/db/dal/email-list.ts`, `scripts/seed.ts`). Keep that setup step in fresh database workflows.
- **Sessions:** Better Auth stores sessions in Postgres; proxy, role gate and individual pages may check session/current user separately (`src/proxy.ts`, `src/components/auth/verified-role-gate.tsx`, `src/lib/auth/access.ts`). Measure request query counts and latency; consolidate request-local checks where safe. Do not add a distributed session cache without evidence.

## Around 100k users

- **Admin list/query design:** `%term%` searches on users, contacts and subscribers and exact filtered counts become expensive as tables grow (`src/server/db/dal/admin-users.ts`, `contact-submission.ts`, `email-list.ts`). Bound query length and page size, inspect plans, then add indexes tailored to observed filters; consider keyset pagination for deep traversal.
- **Verification and session maintenance:** application tokens share Better Auth's `verification` table, and some public/2FA verification requests delete expired rows by prefix during foreground requests (`src/server/db/dal/email-list.ts`, `src/server/account/two-factor.ts`). Move expiry cleanup to scheduled maintenance when table volume warrants it, with bounded batches and indexes supported by plans. Auth/session retention policy and database maintenance need verification.
- **Email reliability:** At material signup/reset volume, provider latency/rate limits and retries can dominate. A Postgres outbox plus a small worker may be justified if lost or delayed email becomes measurable; it can be introduced without microservices. There is no worker today (`src/server/email`, `src/lib/auth/index.ts`).
- **Uploads:** Direct S3 transfer avoids routing image bytes through Next (`src/lib/uploads/avatar.ts`, `src/server/routes/uploads.ts`). Budget S3/CDN bandwidth and stale/orphan avatar cleanup; decide whether upload-key ownership/existence should be recorded when user profiles become security-sensitive.

## Around 1M+ users

If active usage and concurrency actually reach this level, capacity-plan Postgres IOPS/storage, connection budgets, replication/failover, auth/session volume, high-cardinality search and email throughput from measurements. Read replicas or partitioning may become useful for measured read or retention pressure, but the current schema/traffic does not justify prescribing them. More Next replicas are feasible for most request paths because durable state is in Postgres/S3; detached welcome email remains the clear exception (`src/lib/auth/index.ts`). Verify a trusted client identity and add a durable delivery path before claiming fully hardened horizontal scaling.

## Premature optimization

Do not split the app into microservices, add a general repository/Clean Architecture layer, introduce Redis for all reads/sessions, add a queue for every email, or shard/partition Postgres solely from user-count estimates. The current single Next deployable, Drizzle DAL, transaction on email subscription, explicit default-list seed, and direct-to-S3 uploads are sensible (`src/server/routes/index.ts`, `src/server/db/dal/email-list.ts`, `src/lib/uploads`). First bound queries, establish metrics and fix correctness/abuse boundaries.
