# System context

## What this repository is

Mirage is a Next.js starter platform, not a domain-specific finished product. Its public landing page advertises reusable product plumbing: registration and login, account and admin workspaces, Postgres-backed API routes, a waitlist/newsletter, guides/articles, and a contact form (`src/app/page.tsx`, `README.md`, `src/lib/metadata.ts`). Do not infer a larger product domain from the repository name.

## Stack and boundaries

- Next.js 16 App Router, React 19, TypeScript, Tailwind 4, Biome (`package.json`, `src/app`). The root layout owns fonts, metadata and global styles (`src/app/layout.tsx`).
- Better Auth owns credentials, sessions, Google OAuth when configured, email verification, password reset, admin operations, impersonation, and two-factor authentication (`src/lib/auth/index.ts`, `src/app/(backend)/api/auth/[...all]/route.ts`). Its Postgres tables use a Drizzle adapter (`src/server/db/dal/auth.ts`).
- Elysia runs inside a Next route handler for application API operations (`src/app/(backend)/api/[[...route]]/route.ts`, `src/server/routes/index.ts`). Browser code uses Eden for some routes (`src/lib/api/client.ts`) and `fetch` for others. Better Auth's client is separate (`src/lib/auth/client.ts`).
- Drizzle and `postgres` access PostgreSQL. The shared process connection has a pool cap of 5 in development and 10 in production (`src/server/db/index.ts`). `docker-compose.yml` supplies only a local PostgreSQL 17 instance. Migrations are committed under `drizzle/` and configured by `drizzle.config.ts`.
- Fumadocs compiles local MDX in `content/guides` and `content/articles`; content is loaded through `src/lib/content-source.ts` and rendered in `(written-content)` routes. This is file-backed content, not database content.
- Resend sends transactional emails (`src/server/email`). An S3-compatible AWS upload profile signs direct browser-to-object-storage avatar uploads through `@marinedotsh/upload-sdk` (`src/lib/uploads/server`, `src/server/routes/uploads.ts`). The public URL is derived from `NEXT_PUBLIC_UPLOAD_BASE_URL`.

## Feature and module ownership

`src/app` defines URLs, layouts, server-rendered pages, one contact-management Server Action, API adapters and content OG image handlers. `src/components` holds client forms, admin tables and shared UI primitives. `src/server/routes` handles Elysia HTTP validation and authorization. `src/server/account` holds email-change and two-factor workflows. `src/server/db/dal` holds Drizzle queries and some email-list workflow rules. `src/server/db/schema` owns auth, contact and email-list tables. `src/zod` contains request and form schemas. `src/lib/auth` owns Better Auth configuration, access checks, roles and hooks. `src/lib/uploads` separates browser helpers, key validation and server signing. `src/server/email` owns provider configuration, senders and templates. `src/lib/metadata`, `content/`, and `src/components/content` form the published-content path.

## Data model and flows

Auth uses `user`, `session`, `account`, `verification`, and `twoFactor` tables (`src/server/db/schema/auth-schema.ts`). The `user.role` text field is normalized into `user` and `admin` roles; every recognized user receives the `user` role (`src/lib/auth/roles.ts`). `contact_submission` stores form messages and status. `email_list`, `email_contact`, and `email_subscription` store list definitions and subscriber state with a unique contact/list pair (`src/server/db/schema/contact-submission.ts`, `src/server/db/schema/email-list.ts`). Verification rows also carry application email-change, 2FA email-code and email-list tokens.

A protected page first meets `src/proxy.ts` for a session redirect, then the server `VerifiedRoleGate` in the account/admin layout checks the current database user and role. Sensitive pages also call `requireAdmin` before querying (`src/components/auth/verified-role-gate.tsx`, `src/lib/auth/access.ts`). These are separate checks, not a shared cached result. Elysia routes use `elysiaAuth` macros (`src/server/routes/auth.ts`); Better Auth endpoints enforce their own plugin permissions. The `/api` route is outside the proxy matcher, so endpoint authorization is essential.

Client forms call Better Auth endpoints, Elysia endpoints, or a Server Action. For example, public email signup posts to `/api/email-list`; the route validates origin, applies durable public-write limits and Zod validation, then a Drizzle transaction upserts contact/subscription rows for an existing active list. Built-in lists are created by the explicit `pnpm db:seed` setup command, not by signup requests. If verification is required, the route stores a token and sends through Resend; `/api/email-list/verify` consumes the token (`src/components/email-list/email-signup-form.tsx`, `src/server/routes/email-list.ts`, `src/server/db/dal/email-list.ts`, `scripts/seed.ts`). Contact submission follows a similar route but only inserts a message (`src/server/routes/contact.ts`). Admin contact status mutations use the Server Action in `src/app/admin/contact-submission/all/actions.ts` and call `revalidatePath`.

Avatar upload requests a short-lived signed multipart upload after session/origin checks; the browser uploads directly to S3, then writes the returned avatar key through Better Auth's profile endpoint (`src/lib/uploads/avatar.ts`, `src/server/routes/uploads.ts`, `src/components/account/account-profile-form.tsx`, `src/lib/auth/hooks.ts`). Image-key syntax is checked; object ownership or existence is not established by the hook.

## Runtime and deployment assumptions

The implementation assumes a Node-capable Next runtime (Postgres client, Elysia node adapter, Node crypto, email and upload signing). One logical PostgreSQL database stores auth and product data. A stable public origin must match `NEXT_PUBLIC_BASE_URL`, Better Auth URL and OAuth callback settings (`src/lib/env.ts`, `src/lib/auth/index.ts`). `RESEND_API_KEY` and `EMAIL_FROM` are required when production email is used; upload credentials are checked when signing (`src/server/email/config.ts`, `src/lib/uploads/server/env.ts`). The repository includes local Docker Compose and Next start/build scripts, but no production container, infrastructure manifest, CI pipeline, monitoring setup, worker or deployment topology. **Unknown / needs verification:** actual host, database service and pooling layer, CDN/object permissions, backup policy, traffic, email provider settings and production runtime configuration.

## Architectural decisions and known weaknesses

The application is a single deployable Next app with one logical Postgres database. Its App Router pages read the DAL directly, while clients use Better Auth/Elysia. This is appropriate for the present feature set. There is no general service/repository abstraction or job queue. `src/server/account` is a focused workflow layer, but `src/server/db/dal/email-list.ts` mixes database queries with subscription rules and token lifecycle. Some DAL modules import query types from `src/components/admin`, which reverses the intended server-to-UI dependency (`src/server/db/dal/admin-users.ts`, `src/server/db/dal/contact-submission.ts`). Admin account/session deletes and 2FA persistence now live in focused DAL modules; `pnpm depcruise` passes as of 2026-09-13.

The main remaining operational weaknesses are unbounded admin contact/subscriber reads (`src/server/db/dal/contact-submission.ts`, `src/server/db/dal/email-list.ts`) and detached welcome-email delivery. Public-form and custom account-email limits now use durable Postgres budgets; Better Auth's own limiter also uses database storage. Admin APIs require both the admin role and a verified email: the Elysia macro checks both, and the Better Auth route wrapper rejects unverified admins (`src/server/routes/auth.ts`, `src/app/(backend)/api/auth/[...all]/route.ts`). Email-change, email-list verification, and 2FA state transitions use transactional token claims and focused DAL functions. Welcome email remains fire-and-forget from an auth database hook (`src/lib/auth/index.ts`). These warrant targeted fixes and measurement, not a framework rewrite. See `ARCHITECTURE_REVIEW.md` for severity and evidence.
